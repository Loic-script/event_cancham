# Event

[![Vérification](https://github.com/Loic-script/event_cancham/actions/workflows/ci.yml/badge.svg?branch=dev)](https://github.com/Loic-script/event_cancham/actions/workflows/ci.yml)

Application [Next.js 16](https://nextjs.org) (App Router, TypeScript, Tailwind CSS) connectée à une base **PostgreSQL 17** via [Prisma 7](https://www.prisma.io).

## Prérequis

- Node.js 20+ (testé avec Node 24)
- PostgreSQL 17 en service local sur le port 5432

## Mise en route

1. **Configurer la connexion** : copiez `.env.example` vers `.env` (fichier non versionné), puis remplacez `VOTRE_MOT_DE_PASSE` par le mot de passe de l'utilisateur `postgres` (celui choisi à l'installation de PostgreSQL).

   ```bash
   cp .env.example .env
   ```

   ```env
   DATABASE_URL="postgresql://postgres:VOTRE_MOT_DE_PASSE@localhost:5432/event_db?schema=public"
   ```

2. **Installer les dépendances** (le client Prisma est généré dans la foulée, même sans `.env` : `DATABASE_URL` n'est nécessaire que pour les migrations et au démarrage, ce qui permet aussi de construire une image Docker sans la base) :

   ```bash
   npm install
   ```

3. **Créer la base et les tables** (la base `event_db` est créée automatiquement si elle n'existe pas) :

   ```bash
   npm run db:migrate
   ```

4. **Insérer les données d'exemple**, dont le compte de démonstration nécessaire pour se connecter :

   ```bash
   npm run db:seed
   ```

5. **Lancer le serveur de développement** :

   ```bash
   npm run dev
   ```

   Ouvrez [http://localhost:3000](http://localhost:3000) : l'application demande de se connecter. Comptes de démonstration créés par le seed : `faneva.loic@event-studio.mg`, `membre@exemple.mg` et `admin@exemple.mg`, avec le mot de passe `SEED_PASSWORD` s’il est défini, sinon un mot de passe tiré au hasard et affiché par le seed (à noter). Le seed refuse de se lancer en production.

## Tests automatisés

- **Tests unitaires et de bibliothèques** (`tests/*.test.ts`, `npm test`) : règles pures (coordonnées, formats, blocs, limite de connexion) et, sur une base PostgreSQL de test, les bibliothèques rendez-vous B2B (réservations, validation, expiration), billets et scanner (codes, verdicts, encaissement), parcours d’accueil (étapes, page après la connexion), défis (participations, jury, relevé) et paiements (tentative reprise, accès ouvert une seule fois, échec et montant différent sans effet). `tests/vanillapay.test.ts` vérifie sans réseau la signature des notifications et la lecture des deux formats. Chaque test crée ses comptes (`test-auto-…@exemple.mg`) et les supprime.
- **Base de test** : `DATABASE_URL_TEST` dans `.env` (voir `.env.example`), une base à part dont le nom contient « test » ou « ci » (`tests/outils/base.ts` refuse le reste et la substitue à `DATABASE_URL` avant de charger Prisma). La créer une fois : `CREATE DATABASE event_test;` puis `DATABASE_URL="<adresse de test>" npx prisma migrate deploy`. Sans la variable, ces tests sont ignorés et `npm test` reste vert.
- **Scénarios navigateur** (`tests/e2e/*.spec.ts`, Playwright, `npm run test:e2e`) : `playwright.config.ts` démarre `next start` sur le port 3217 avec la base de test, sans e-mails ni Google ; il faut un `npm run build` à jour. Scénarios : inscription par le formulaire puis parcours d’accueil complet, connexion (mot de passe refusé ou accepté, blocage après cinq échecs), demande de rendez-vous depuis l’annuaire validée par l’autre participant, scanner (validé, déjà scanné, paiement à l’entrée), message lu par son destinataire, règlement du billet par le simulateur Vanilla Pay (réussi, échoué, montant différent, retour sans notification). Les comptes sont créés et supprimés par `tests/e2e/bd.ts`, lancé dans un processus `tsx` à part (le client Prisma généré est en ESM).

## Intégration continue

À chaque push ou pull request sur `dev` (ou `main`), GitHub Actions (`.github/workflows/ci.yml`) démarre un PostgreSQL 17 vide, installe le projet, applique toutes les migrations (`prisma migrate deploy`, ce qui vérifie la chaîne de migrations depuis zéro), puis lance `npm run verifier` (lint, types, tests, build) et enfin les scénarios navigateur Playwright sur ce build (`npm run test:e2e`, rapport joint en cas d’échec). Le résultat apparaît sur chaque commit et dans l’onglet *Actions* du dépôt ; aucune clé réelle n’est nécessaire (ni Resend, ni Google). Un nouveau push sur la même branche annule la vérification en cours. Pour interdire de fusionner quand c’est rouge : *Settings → Branches → règle sur `dev` → Require status checks* avec « Migrations, lint, types, tests, build et navigateur ».

## Espace participant

Plateforme du gala **La Traversée · Gala des 10 ans** (CanCham Madagascar, 18 décembre 2026). Pensée d'abord pour le téléphone, utilisé pendant la soirée, sans négliger l'ordinateur.

| Route            | Rôle                                                                                     |
| ---------------- | ---------------------------------------------------------------------------------------- |
| `/connexion`     | Page de connexion (e-mail, mot de passe), accessible sans session                        |
| `/inscription`   | Création de compte (nom, prénom, entreprise, rôle, e-mail, téléphone, mot de passe), accessible sans session ; mène au parcours d’accueil. Champs préremplissables par l’adresse, pour le bouton « Réserver mon billet » de cancham.mg : `?prenom=&nom=&entreprise=&role=&email=&telephone=` (seul le mot de passe reste à saisir) |
| `/bienvenue`     | Parcours d’accueil en étapes (photo, entreprise, défis), après l’inscription et à chaque connexion tant qu’il n’est pas terminé (voir « Parcours d’accueil ») |
| `/`              | Accueil : stories, fil d’actualité, emplacements promotion, compte à rebours                  |
| `/billet`        | Billet d'entrée du participant connecté (code et QR propres à son compte, titulaire, mention si le billet n’est pas réglé) dans une maquette de téléphone, plein écran, partage et téléchargement |
| `/messages`      | Messagerie en base : conversations avec les participants et l’équipe CanCham, puis `/messages/[id]` avec émojis et messages vocaux |
| `/profil`        | Profil : photo et couverture, fiche, coordonnées et mot de passe, billet, suppression du compte (voir plus bas) |
| `/defis`         | Renvoie vers `/defis/pitch` ; `/defis/pitch` et `/defis/tombola` sont les deux défis (voir plus bas) |

- **Annonces en base** : tables `annonces` (titre, message, type, lien interne, photo envoyée par `/api/fil/images`) et `annonces_vues` (migration `20261020140000_annonces`). L’équipe publie, renvoie ou supprime depuis `/admin/annonces` (historique avec le nombre de participants qui ont vu chaque annonce ; actions dans `src/app/(app)/annonces/actions.ts`). Le layout charge les annonces des 60 derniers jours (`annoncesPour`, `src/lib/annonces.ts`) : la plus récente non vue s’ouvre en fenêtre, une seule fois par compte (`marquerAnnoncesVues`), et toutes restent dans la cloche.
- **Rendez-vous B2B en base** : table `rendez_vous_b2b` (demandeur, destinataire, créneau = indice dans `CRENEAUX`, emplacement = indice dans `LIEUX`, statut `ATTENTE`/`CONFIRME`/`DECLINE`/`ANNULE`, note privée de chaque côté ; migration `20261020160000_rendez_vous_b2b`, logique dans `src/lib/rendezvous.ts`). Une demande réserve l’emplacement 48 h ; sans réponse elle expire et le libère. Un emplacement ne sert qu’une fois par créneau et une personne n’a qu’un rendez-vous par créneau, vérifié sous verrou (`pg_advisory_xact_lock`) pour les demandes simultanées. Depuis l’annuaire (« Rendez-vous ») et `/rdv` : demander, valider, décliner, proposer un autre créneau (la demande reçue est déclinée et une nouvelle part vers l’autre), annuler, noter (actions dans `src/app/(app)/rdv/actions.ts`). Demandes reçues et réponses récentes dans la cloche.
- **Défis en base** : table `participations_defis` (une ligne par participant et par défi, `pitch` ou `tombola` : lien de la vidéo ou de la publication, dernier relevé de réactions, commentaires et partages, note du jury sur 20 et appréciation, retrait du classement ; migration `20261020180000_participations_defis`, lecture dans `src/lib/defis.ts`, actions dans `src/app/(app)/defis/actions.ts`). Un nouvel envoi de pitch remplace le précédent et efface sa note ; un nouveau lien de publication remet ses réactions à zéro mais garde un éventuel retrait. `GET /api/publications/reactions` lit les réactions sur Facebook et les enregistre sur la publication du compte connecté (même lien) : c’est ce relevé qui classe les publications. Le jury note depuis `/admin/defis/pitch`, l’équipe retire ou rétablit une publication depuis `/admin/defis/tombola`.
- **Galerie, stories et promotions en base** : tables `photos_galerie` (une ligne par fichier de `stockage/photos`, auteur, officielle quand elle vient de l’équipe), `stories` (photo, texte, auteur) et `promotions` (emplacements 0 à 3 de l’accueil) ; migration `20261020200000_galerie_stories_promotions`, qui crée les trois stories de départ de la CanCham. Lecture dans `src/lib/galerie.ts`, actions dans `src/app/(app)/galerie/actions.ts`. `POST /api/photos` inscrit la photo dans la galerie (équipe ou participant validé) ; l’équipe retire n’importe quelle photo, un participant les siennes ; la suppression d’un compte emporte ses photos partagées. Les photos de stories et de promotions passent par `POST /api/fil/images` et sont effacées avec leur story ou leur promotion. Au démarrage, les photos déjà envoyées avant la mise en base (fichiers sans ligne) sont inscrites comme photos de l’équipe. Un emplacement promotion vide n’apparaît pas chez les participants ; sans aucune promotion, ils voient une invitation à écrire à l’équipe.
- **Livre d’or en base** : table `livre_or` (auteur, vidéo envoyée sur `/api/videos`, durée lue par le navigateur, message de 500 caractères au plus, statut `ATTENTE`/`VALIDE`/`REFUSE` ; migration `20261020220000_livre_or`, lecture dans `src/lib/livre.ts`, actions dans `src/app/(app)/livre/actions.ts`). Un participant dépose une vidéo et un message (trois en attente au plus) et peut retirer ce qui n’est pas encore publié ; l’équipe valide, refuse ou retire du livre, retouche le message (« Corriger la ponctuation » applique `ajusteSousTitres`) et supprime définitivement, vidéo comprise. La suppression d’un compte efface ses vidéos. Les exemples fictifs et les « sous-titres automatiques » (qui n’existaient pas) sont retirés.
- **Billets et entrées en base** : chaque compte reçoit à sa création un code de billet tiré au hasard par la base (colonne `code_billet`, `TRV26-` suivi de 8 caractères, unique, impossible à deviner à partir du numéro de compte ; les comptes existants en reçoivent un à la migration `20261020230000_billets_entrees`). `/billet` et la fenêtre « Mon billet » du profil affichent le code et le QR du participant connecté, et signalent un billet pas encore réglé (`billet_paye`). Le scanner vérifie chaque code côté serveur (`src/lib/billets.ts`, actions dans `src/app/(app)/admin/scanner/actions.ts`) et enregistre l’entrée dans `entrees_gala` (une par participant, avec l’administrateur qui a scanné) : entrée validée, paiement en attente (bouton « Paiement reçu : valider l’entrée », qui marque le billet payé), déjà scanné (avec l’heure d’entrée) ou billet inconnu (code absent ou compte non validé). « Effacer » remet toutes les entrées à zéro, après confirmation.
- **Notifications tirées de la base** : la cloche ne lit plus de journal gardé dans le navigateur. L’équipe y voit, en plus des messages et des inscriptions, les publications des participants, les envois de vidéo pitch et les participations au Défi 2, les vidéos du livre d’or à valider et les photos partagées des 7 derniers jours (`activiteAdmin`, `src/lib/activite.ts`, servi avec `/api/admin/comptes-recents`) ; les participants y voient les actualités et stories publiées par la CanCham (`activiteParticipant`, chargé par `src/app/(app)/layout.tsx`). L’état « lue » reste propre à chaque navigateur.
- **Messagerie en base** : tables `conversations` (clé `u12-u34` entre deux comptes, ou `equipe-u12` pour un participant et l’équipe CanCham), `conversation_participants` (date de lecture) et `messages` (texte ou vocal), migration `20261020120000_messagerie`, logique dans `src/lib/messagerie.ts`. « Écrire » (annuaire) et le crayon « Nouveau message » passent par `/messages/avec/[userId]` ; la bulle d’aide par `/messages/equipe` ; l’équipe répond depuis `/admin/messagerie` (`/admin/messagerie/avec/[userId]` pour écrire à un participant), ses messages partent au nom de l’équipe. Envoi par l’action `envoyerMessage` ; la conversation ouverte demande les nouveaux messages toutes les 4 s (`actualiserConversation`), marque la lecture et affiche « Vu ». Vocaux : `POST /api/messages/[id]/audio` (WebM, Ogg ou M4A vérifiés, 4 Mo et 2 min au plus, rangés dans `stockage/messages`), lus par `GET /api/messages/audio/[id]` réservé aux comptes de la conversation. Pastilles du menu et notifications : `GET /api/messages/non-lus` (toutes les 30 s). La suppression d’un compte efface ses conversations et leurs vocaux.
- **Développement** : le badge des outils de développement Next.js est désactivé dans `next.config.ts`, car il recouvrait la barre de saisie sur mobile ; les erreurs restent affichées.
- **Charte graphique CanCham** (document « Nouvelle charte CanCham ») : blanc `#ffffff`, bleu foncé `#0f1d2c` (texte, compte à rebours), rouge vif `#ad0707` (actions), vert `#007140` (états, succès) et dégradé linéaire 90° `#ad0707 → #007140` (barre sous les titres de page, bouton Billet, anneau des stories, halos de l'écran du billet). Montserrat en gras pour les titres et les étiquettes (`font-display`, `font-mono`), Open Sans pour les textes (`src/app/layout.tsx`). Les jetons sont dans `src/app/globals.css` (classe `theme-light` ; un thème sombre `theme-dark` reste disponible). Logos des réseaux sociaux redessinés en SVG (`src/components/app/BrandLogos.tsx`). Correspondance des jetons : vert `--palm` pour les fonds d'action et `--palm-ink` pour le texte vert, rouge `--leaf` / `--leaf-ink`, or `--gold`, surfaces translucides `--surface` et opaques `--elevated`. Le billet garde un papier blanc grâce à l'îlot `theme-light`. Fraunces pour les titres, Geist pour l'interface. Animations CSS discrètes (entrée de page en cascade, halos de la bannière, téléphone du billet qui se pose, cœur qui bondit, bulles qui arrivent), `prefers-reduced-motion` respecté, zones tactiles d'au moins 44 px, cartes pleine largeur sur téléphone (classe `m-bleed` de `src/app/globals.css` : collées aux bords gauche et droit, sans arrondi ni bordure latérale, comme les publications Facebook), zones sûres des téléphones à encoche.

## Comptes et connexion

- **Tables** : `users` (e-mail unique, mot de passe haché, nom, poste, entreprise, ville, pays) et `sessions` (empreinte SHA-256 du jeton, utilisateur, expiration), définies dans `prisma/schema.prisma` et créées par la migration `20261009140000_users_sessions`.
- **Mots de passe** : hachés avec `scrypt` de Node (`src/lib/password.ts`), jamais stockés en clair ; la comparaison est à temps constant.
- **Sessions** : jeton aléatoire de 32 octets dans un cookie `session` (`httpOnly`, `SameSite=Lax`, `Secure` en production, 30 jours), dont seule l'empreinte est en base (`src/lib/session.ts` : `createSession`, `getCurrentUser`, `requireUser`, `destroySession`).
- **Page `/connexion`** (`src/app/connexion/`, composants `src/components/auth/`) : écran partagé (`AuthScene.tsx`, jetons locaux dans `auth.module.css`). Depuis le 27 octobre 2026, `/connexion` et `/inscription` suivent la **charte CanCham** (prop `charte="cancham"`, bloc `.cancham` : bleu foncé `#0f1d2c`, rouge vif `#ad0707` pour les boutons, liens et focus, dégradé rouge → vert sur le mot accentué du titre et en filet du panneau, Montserrat pour les titres et Open Sans pour le texte, logo CanCham horizontal blanc `public/cancham/logo-blanc.png`) ; les autres pages qui partagent cet écran (mot de passe oublié, compléter le profil, attente, paiement) gardent la charte Impact 261 décrite ci-dessous (IBM Plex Sans, orange, logo IMPACT 261). À gauche, un panneau bleu nuit uni : logo blanc IMPACT 261 (`public/impact261/logo-blanc.svg`), emblème doré « 10 ans » (`public/connexion/10-ans.png`), titre blanc avec accent pêche, compte à rebours jusqu'au gala sur ordinateur (`AuthCountdown.tsx`, valeur initiale calculée par le serveur), fond photo qui change toutes les 5 secondes en fondu enchaîné avec un léger zoom (`PanelSlideshow.tsx`, six photos d'événements CanCham dans `public/connexion/fonds/`, sous un voile bleu nuit ; photo suivante chargée juste avant son tour, pause quand l'onglet est masqué, image fixe si l'utilisateur limite les animations), date et lieu du gala. À droite, le formulaire sur fond blanc, dont le bord s'avance sur la photo en une courbe douce (ellipse blanche en `::before`, variable `--vague` ; courbe horizontale en haut du formulaire sur mobile) : libellés visibles, erreurs affichées sous le champ concerné (e-mail vérifié à la sortie du champ, focus sur le premier champ en erreur), indicateur de chargement sur le bouton, bouton principal orange foncé `#c94d0c` (contraste 4,6:1 avec le texte blanc), « Mot de passe oublié ? » à côté du libellé du mot de passe. Sur mobile, l'en-tête (même fond photo, voile plus soutenu) est suivi directement du formulaire. Le formulaire appelle l'action serveur `login` (`src/app/connexion/actions.ts`) ; après connexion, retour vers la page demandée (`?next=…`, chemins internes seulement). Les boutons Google et Facebook sont des emplacements (« arrive bientôt ») ; « Mot de passe oublié ? » mène vers `/mot-de-passe-oublie`, encore à construire.
- **Page `/inscription`** (`src/app/inscription/`, formulaire `RegisterForm.tsx`) : même écran, en miroir sur ordinateur (formulaire à gauche, photo à droite, vague tournée vers la droite : prop `inverse` d'`AuthScene`), mêmes règles de formulaire (libellés visibles, erreurs par champ), champs tous obligatoires : nom, prénom, entreprise, rôle (enregistré dans `role`, le poste affiché dans l'annuaire), e-mail, téléphone (7 chiffres au moins, `+`, espaces, points, tirets et parenthèses acceptés) et mot de passe (8 caractères minimum). L'action serveur `register` vérifie les champs, refuse un e-mail déjà utilisé (comparaison en minuscules), hache le mot de passe, crée l'utilisateur, ouvre la session et renvoie vers la page demandée. Sur ordinateur, seule la colonne du formulaire défile (`.defile` dans `AuthScene.tsx`, posée en absolu pour ne pas allonger la page) : la photo, le titre, le compte à rebours et les infos du gala restent fixes.
- **Transition connexion ↔ inscription** : les blocs d'`AuthScene` portent le même nom sur les deux pages (`<ViewTransition>` de React, sans configuration dans l'App Router) ; le panneau photo et le formulaire glissent vers leur nouvelle place en 0,7 s, le titre, les infos et la carte du formulaire passent le relais (l'ancien texte s'efface, puis le nouveau apparaît). Styles `auth-glisse`, `auth-relais` et `auth-garde` dans `src/app/globals.css`, désactivés si l'utilisateur limite les animations. Sans prise en charge du navigateur, la page change sans animation.
- **Protection des pages** : `src/proxy.ts` redirige vers `/connexion` toute requête sans cookie de session (sauf `/connexion`, `/inscription`, `/mot-de-passe-oublie`, `/api/health`, `/api/auth`, la notification de paiement `/api/paiements/vanillapay`, le simulateur `/simulateur-vanillapay` et les fichiers statiques) et renvoie 401 sur `/api/*`. La session est ensuite vérifiée en base dans les layouts `src/app/(app)/layout.tsx` et `src/app/decouvrir/layout.tsx`, la page `/events` et les routes `/api/events` (création réservée aux administrateurs). `/api/health` répond seulement `{ ok }` sans rien dévoiler de l’installation.
- **Limite des tentatives de connexion** (`src/lib/connexion-limite.ts`, table `tentatives_connexion`, migration `20261022000000_tentatives_connexion`) : après 5 échecs en 15 minutes sur une adresse e-mail, ou 30 depuis une même adresse IP, la connexion répond « Trop de tentatives. Réessayez dans N minutes » sans même vérifier le mot de passe ; une connexion réussie remet le compteur de l’adresse à zéro. Les échecs sont en base, donc comptés même après un redémarrage.
- **En-têtes de sécurité** (`next.config.ts`) : `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy` (caméra et micro pour le site seul), `Strict-Transport-Security`.
- **Déconnexion** : bouton « Se déconnecter » du profil (action serveur `logout`), qui supprime la session en base et le cookie.
- **Synchronisation avec la plateforme** : `src/app/(app)/layout.tsx` exige une session (`requireUser`) et transmet l'utilisateur connecté à toute l'interface (`SessionIdentityProvider` dans `src/components/profile/useProfile.ts`) : `useProfile()` reprend son prénom, son nom, son e-mail et son entreprise depuis la base, et les retouches de profil faites dans le navigateur sont rangées par compte. `src/app/(app)/admin/layout.tsx` réserve tout le back-office aux administrateurs (`requireAdmin`) ; le lien « Back-office CanCham » n'apparaît que pour eux, un administrateur arrive directement sur `/admin` après connexion, et « Se déconnecter » dans la barre latérale ferme vraiment la session.
- **Niveaux d'accès** : colonne `acces` des utilisateurs (`MEMBRE` par défaut, ou `ADMIN`, migration `20261015120000_acces_utilisateurs`), lue avec la session ; `requireAdmin()` (`src/lib/session.ts`) renvoie vers l'accueil un compte qui n'est pas administrateur. Comptes de test créés par le seed : membre `membre@exemple.mg` et administrateur `admin@exemple.mg`, mot de passe `SEED_PASSWORD` ou tiré au hasard (voir « Démarrage »). Aucun compte à mot de passe fixe.
- **Annuaire et profils en base** : les annuaires (`/annuaire` et `/admin/participants`) affichent les comptes membres de la base (`src/lib/annuaire.ts`), et non plus des fiches d'exemple ; l'annuaire des participants n'affiche pas l'utilisateur connecté. Le profil (entreprise, fonction, secteur, présentation, téléphone, site web) est enregistré en base à chaque modification (`updateProfile` appelle l'action `enregistrerProfil`, colonnes ajoutées par la migration `20261015130000_profil_annuaire`). Depuis le back-office, « Voir le profil » modifie la fiche et l'état du billet en base (`billet_paye`).
- **Validation des inscriptions** : colonne `statut` des utilisateurs (`EN_ATTENTE` par défaut, `ACTIF` ou `REFUSE`, date `decision_le`, migration `20261019170000_statut_compte` qui laisse actifs les comptes existants). Après l'inscription et le parcours d'accueil, un membre règle son billet sur `/paiement` (voir « Paiement du billet ») et n'entre dans l'espace participant qu'une fois actif ; `/en-attente` ne sert plus qu'aux comptes refusés : `requireMembreActif()` dans les layouts `(app)` et `decouvrir`, `refusSiSansAcces()` / `aAccesEspace()` dans les API des membres (`src/lib/session.ts`). Les administrateurs ont toujours accès. Page `/admin/acces` (« Demandes d'accès », groupe Participants, pastille du nombre en attente) : onglets En attente / Validés / Refusés, recherche, coordonnées cliquables ; « Donner l'accès », « Refuser », « Retirer l'accès » (retour en attente). L'annuaire n'affiche que les membres actifs. Un paiement confirmé passe le statut à `ACTIF` automatiquement ; « Donner l'accès » reste l'alternative manuelle (paiement hors ligne).
- **Mot de passe oublié** : `/mot-de-passe-oublie` (lien « Mot de passe oublié ? » de la connexion, adresse déjà saisie reprise) envoie un e-mail avec un lien `/mot-de-passe-oublie/<jeton>` valable 1 heure et utilisable une fois (table `reinitialisations_mot_de_passe`, seule l'empreinte SHA-256 du jeton est gardée ; un e-mail par minute au plus par compte). La réponse est la même que l'adresse ait un compte ou non. Le nouveau mot de passe ferme toutes les sessions du compte puis connecte le navigateur, avec la même page d’arrivée qu’après une connexion (`pageApresConnexion`). **Compte créé par un administrateur** (« Créer un compte » dans l’annuaire du back-office, `creerParticipant`) : le membre reçoit « Votre compte La Traversée est prêt : créez votre mot de passe » avec un bouton vers `/creer-mot-de-passe/<jeton>` (même table de jetons, valable 7 jours, usage unique, `DUREE_CREATION_MINUTES`), où il choisit son mot de passe et entre directement ; aucun mot de passe ne circule par e-mail. Si l’e-mail ne peut pas partir, le lien est affiché une seule fois à l’administrateur pour qu’il le transmette ; un lien expiré se remplace par « Mot de passe oublié ? ». Envoi par l'API de Resend (`src/lib/courriel.ts`) : `RESEND_API_KEY`, `COURRIEL_EXPEDITEUR` (domaine vérifié chez Resend), `COURRIEL_EQUIPE` (adresse de réponse), et `APP_URL` obligatoire en production pour construire le lien ; sans `RESEND_API_KEY` en développement, le lien s'affiche dans le terminal du serveur.
- **Alerte des nouvelles inscriptions** : chaque inscription (formulaire, ou Google et Facebook une fois le profil complété) envoie un e-mail à tous les comptes administrateurs (`src/lib/alertes-admin.ts`, après la réponse grâce à `after()`) : nom, entreprise, rôle, e-mail, téléphone, mode d’inscription et lien vers `/admin/acces`. Une erreur d’envoi est journalisée sans bloquer l’inscription. Modèles des e-mails : `src/lib/courriels.ts`, avec le logo Impact 261 en tête sur une bande bleu nuit (image intégrée `cid:logo-impact`, fichier `public/impact261/logo-courriel.png` joint par `envoyerCourriel`).
- **Parcours d’accueil** (`/bienvenue`, `src/components/bienvenue/`, logique dans `src/lib/parcours.ts`, actions dans `src/app/bienvenue/actions.ts`) : ouvert automatiquement après l’inscription et à chaque connexion tant qu’il n’est pas terminé (`pageApresConnexion`, utilisé par la connexion, l’inscription, Google et Facebook et « Compléter votre profil »). Plein écran, hors coquille, avec une photo de l’événement filtrée en bleu nuit par étape : introduction, photo de profil et couverture, « vous et votre entreprise » (prénom, nom, entreprise, fonction et téléphone préremplis depuis l’inscription, mêmes règles ; secteur et présentation à compléter), Défi 1 (lien de la vidéo pitch), Défi 2 (lien de la publication « J’y serai »), puis récapitulatif avec compte à rebours. Chaque étape est enregistrée dès « Suivant » (photo via `/api/profil/photo`, entreprise sur le compte, défis via les actions des défis) ; on peut passer une étape, revenir en arrière (l’étape courante vit dans l’adresse, `?etape=`, donc le bouton Retour du navigateur fonctionne) ou « Terminer plus tard ». Une étape faite se lit dans les données du compte ; la table `parcours_accueil` (migration `20261021000000_parcours_accueil`) garde les étapes passées et la date de fin. Un compte en attente de validation fait les quatre étapes, défis compris (les actions des défis acceptent les comptes en attente ; leurs participations n’apparaissent au jury et au classement qu’une fois le compte validé, `participants()` dans `src/lib/defis.ts`), puis voit « Il reste votre billet » et passe au règlement (`/paiement`). Le profil affiche un bandeau « Reprendre » tant que le parcours n’est pas terminé ou qu’il reste des étapes passées (`reprendreParcours` les propose de nouveau). Les administrateurs n’ont pas de parcours.
- **Google et Facebook** : bouton Google sur `/connexion` et en tête de `/inscription` (`BoutonsSociaux.tsx`) ; Facebook est codé mais retiré des boutons et désactivé (`FACEBOOK_ACTIF` dans `src/lib/oauth.ts`) tant que l’app Meta n’est pas en mode Live. `GET /api/auth/google|facebook` part chez le fournisseur (adresse de retour construite avec `APP_URL`, comme `/api/facebook/login` pour les réactions : derrière l’hébergeur, l’origine de la requête serait `localhost`) (état dans le cookie `oauth_etat`, PKCE pour Google), `GET /api/auth/<fournisseur>/callback` lit le profil (`src/lib/oauth.ts`) puis `connecterAvecProfil` (`src/lib/connexion-sociale.ts`) : compte déjà relié (colonnes `google_id`, `facebook_id`), sinon compte de même adresse e-mail confirmée par le fournisseur (relié au passage, sauf un compte administrateur, qui garde son mot de passe), sinon nouveau compte en attente de validation avec un mot de passe aléatoire (« Mot de passe oublié » permet d'en choisir un). Un nouveau compte passe par `/inscription/completer` (entreprise, rôle, téléphone obligatoires, mêmes règles que l'inscription : `src/lib/coordonnees.ts`). Identifiants : `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`, `FACEBOOK_APP_ID` / `FACEBOOK_APP_SECRET` (à défaut `META_APP_ID` / `META_APP_SECRET`) ; adresses de retour à déclarer : `<APP_URL>/api/auth/google/callback` et `<APP_URL>/api/auth/facebook/callback`. Sans identifiants, le bouton affiche « pas encore activée ». Erreurs au retour : `?erreur=refus|etat|email|non-verifie|admin|config|erreur&via=…`.
- **Administrateurs et super admin** : page `/admin/administrateurs` (menu Pilotage), liste en cartes cliquables (super admins en tête, dernière connexion d’après la session la plus récente). Une carte ouvre la fiche « À propos » (`AdminFiche.tsx`) : coordonnées, entreprise et rôle, droits, dates ; le super admin y modifie l’administrateur (`modifierAdmin`), lui retire ses droits ou supprime son compte. Seul le **super admin** (adresses de `SUPER_ADMINS`, `src/lib/super-admin.ts`) ajoute un administrateur, lui retire ses droits ou supprime son compte ; les autres admins voient la liste en lecture seule. Un membre déjà inscrit est promu (et validé), sinon un compte est créé : dans les deux cas, un mot de passe tiré au hasard (`genererMotDePasse`) lui est envoyé par e-mail, et si l’e-mail ne part pas, rien n’est changé. Personne ne peut modifier, rétrograder ou supprimer un super admin depuis la plateforme, ni prendre son adresse. Au démarrage (`src/instrumentation.ts`), chaque adresse de `SUPER_ADMINS` reçoit un compte administrateur ; un compte créé ou repris a un mot de passe inconnu et ses sessions fermées : on y entre par « Mot de passe oublié ». Depuis la fiche participant du back-office, un admin ne modifie que des comptes membres.
- **Photos de profil** : enregistrées sur le compte (colonne `photo`, migration `20261020090000_photo_profil`), et non plus seulement dans le navigateur. « Mon profil » et « Mon compte » (admins) utilisent `ChoixPhotoProfil.tsx` : la photo, réduite à 640 px dans le navigateur, part sur `POST /api/profil/photo` (JPEG, PNG ou WebP vérifié, 5 Mo maximum, rangée dans `stockage/profils`, l’ancienne effacée) ; `DELETE` la retire ; `GET /api/profil/photos/[id]` la sert aux comptes qui ont accès à l’espace. Une ancienne photo gardée dans le navigateur est reprise une fois sur le serveur. `AvatarProfil` (`ui.tsx`) l’affiche en rond, sans anneau (administrateurs, annuaire, fiche participant) ; le fil d’actualité montre aussi la photo des auteurs. **Couverture** : même mécanisme avec `POST`/`DELETE /api/profil/couverture` (colonne `couverture`, migration `20261021010000_couverture_profil`, réduite à 1 600 px, `ChoixCouverture.tsx`), partagé dans `src/lib/profil-images.ts` ; elle sert de bannière à la carte d’identité du profil et à la fiche de l’annuaire (sans couverture, une photo de l’événement). Son cadrage vertical se règle en la faisant glisser (« Repositionner », `CouvertureReglable.tsx`, flèches haut et bas au clavier) depuis le profil ou le parcours d’accueil : colonne `couverture_position` (0 à 100, migration `20261021020000_couverture_position`, action `positionnerCouverture`), remise au centre à chaque nouvelle couverture, reprise par l’annuaire. La suppression d’un compte efface sa photo et sa couverture.
- **Supprimer mon compte** : en bas de `/profil`, après avoir tapé SUPPRIMER (`supprimerMonCompte`). Le compte, ses sessions, publications (et leurs fichiers), j’aime, commentaires et inscriptions au programme sont effacés (`supprimerCompte`, `src/lib/comptes.ts`), ainsi que les j’aime et commentaires des autres sur ses publications ; retour sur `/connexion?compte=supprime`. Le super admin ne peut pas supprimer son compte.
- **Back-office protégé côté serveur** : les routes `/api/admin/*` (`refusSiNonAdmin()`) et les actions de `src/app/(app)/admin/ressources/actions.ts` (`estAdmin()`) refusent tout compte qui n'est pas administrateur (403), en plus du layout `/admin`. Les routes d'envoi (`/api/admin/*`, `/api/videos`) sont exclues de `proxy.ts` pour que leurs fichiers ne soient pas mis en mémoire ni coupés à 10 Mo, et vérifient elles-mêmes la session.
- **Fil d'actualité en base** : tables `publications` (auteur, `equipe` pour les publications au nom de la CanCham, réservées aux administrateurs, texte de 1 200 caractères, photo, vidéo), `fil_jaimes` et `fil_commentaires` (migration `20261019190000_fil_actualite`). J'aime et commentaires visent une cible : `pub:<id>` pour une publication, `actu:<id>` pour un article officiel (`ACTUS`). Les pages `/` et `/admin` chargent le fil côté serveur (`chargerFil`, `src/lib/fil.ts`) avec les vrais compteurs ; les actions de `src/app/(app)/fil/actions.ts` publient, suppriment (auteur ou administrateur, avec j'aime, commentaires et fichiers), basculent un j'aime et lisent, ajoutent ou suppriment un commentaire. Les photos jointes, réduites à 1 080 px dans le navigateur, passent par `POST /api/fil/images` (rangées dans `stockage/fil/`, lues par `GET /api/fil/images/[id]`). Toutes ces opérations exigent un compte validé.
- **Programme en base** : tables `programme` (titre, catégorie parmi `CATS`, heure en texte libre, lieu, places avec 0 pour un accès libre, résumé, détails, photo de `/public/traversee`, ordre) et `programme_inscriptions` (migration `20261019210000_programme`, qui crée aussi les 9 rendez-vous de départ). L’inscription verrouille la ligne du rendez-vous (`SELECT … FOR UPDATE`) pour ne jamais dépasser les places ; elle exige un compte validé. Les modifications de `/admin/programme` sont visibles tout de suite par les participants.
- **Vidéos dans les publications** : le bouton « Vidéo » de l'accueil envoie une vidéo MP4, MOV ou WebM (100 Mo maximum, progression affichée) à `POST /api/videos`, qui la range dans `stockage/videos/` après avoir vérifié son format ; `GET /api/videos/[id]` la diffuse en flux (lecture par morceaux) aux comptes connectés. La publication, enregistrée en base, garde seulement l'adresse de la vidéo.
- **Ajouter un compte sans passer par le formulaire** : dans `prisma/seed.ts` (comme le compte de démonstration) ou via Prisma Studio, avec un e-mail en minuscules et un mot de passe produit par `hashPassword`.

## Paiement du billet (Vanilla Pay)

- **Règle d’accès** : un compte `EN_ATTENTE` suit le parcours d’accueil, puis règle son billet sur `/paiement` ; tant que le paiement n’est pas confirmé, `requireMembreActif()` et `refusSiSansAcces()` le renvoient vers `/paiement` (un compte `REFUSE` reste sur `/en-attente`), et `pageApresConnexion` y mène après la connexion. Un paiement confirmé passe le compte en `ACTIF`, coche `billet_paye` et remplit `paye_le` et `paiement_reference` (migration `20261022020000_paiements`). Les administrateurs ne paient pas.
- **Page `/paiement`** (`src/app/paiement/`, `src/components/paiement/`) : montant (`PAIEMENT_MONTANT_AR`, 500 000 Ar par défaut, 5 000 au moins), ce que le billet débloque, quatre moyens (carte bancaire, MVola, Orange Money, Airtel Money ; logos fournis par la CanCham dans `public/paiement/`, redimensionnés et sans métadonnées), note sur les frais de l’opérateur, « Écrire à l’équipe » (`COURRIEL_EQUIPE`) et déconnexion. L’action `payer` crée ou reprend la tentative (`src/lib/paiements.ts`, table `paiements` : référence `LT-2026-XXXXXX` unique sans caractères ambigus, montant, moyen, `statut` en_cours / reussi / echoue, identifiant de transaction du prestataire, dernière notification, dates) puis envoie le navigateur à l’adresse de paiement de Vanilla Pay (`src/lib/vanillapay.ts` : jeton `GET /webpayment/token` gardé 5 min, `POST /api/webpayment/v2/initiate` avec `panier` = référence, `notif_url`, `redirect_url`, `devise` MGA, `mode_paiement` international ou mobile_money ; pour le mobile money, lien direct vers l’opérateur). Une erreur connue du prestataire est traduite pour le payeur (`messagePourLePayeur`), les autres donnent « Le prestataire de paiement ne répond pas ».
- **Conclusion, une seule fois** : `conclurePaiement(reference, …)` fait une mise à jour conditionnelle `en_cours → reussi` (ou `echoue`) dans une transaction, puis active le compte et écrit le journal (`paiement_reussi`). La notification et la page de retour passent par la même fonction : la seconde ne trouve plus de tentative en cours et ne refait rien. Un montant reçu différent du montant attendu clôt la tentative en `echoue`, n’ouvre rien et est journalisé (`paiement_montant_different`). Après un succès, `after()` envoie le reçu au membre et une alerte aux administrateurs (`courrielRecuPaiement`, `courrielAlertePaiement`).
- **Notification** `POST /api/paiements/vanillapay` (route publique) : le corps est lu brut, la signature HMAC-SHA256 hexadécimale (en-tête `VPI-Signature`, clé `VANILLAPAY_KEY_SECRET`) est comparée en temps constant avant toute lecture ; sans signature valable, 401 et rien n’est fait. Les champs peuvent être en JSON ou en formulaire encodé, à la racine ou sous `Data` (`lireNotification`) ; `montant_mga` prime sur `montant` (paiement par carte en devise). Réponse `{ ok, resultat }` en 200 dès que c’est traité.
- **Retour** `/paiement/retour?ref=` : seules les tentatives du membre connecté sont visibles. Si la notification n’est pas encore arrivée, l’état est demandé au prestataire (`GET /api/webpayment/v2/status/{transaction}?mode_paiement=…`) et conclu de la même façon ; sinon « Confirmation en cours » avec « Recharger ». Trois écrans : paiement reçu (vers l’espace), refusé (réessayer ou autre moyen), en cours.
- **Réglages** : `VANILLAPAY_CLIENT_ID`, `VANILLAPAY_CLIENT_SECRET`, `VANILLAPAY_KEY_SECRET` (côté serveur seulement, jamais journalisées ni envoyées au navigateur), `VANILLAPAY_BASE` (défaut `https://bo.vanilla-pay.net`), `VANILLAPAY_VERSION` (défaut `2023-01-12`), `PAIEMENT_MONTANT_AR`. Dans le back-office Vanilla Pay, déclarer la notification `<APP_URL>/api/paiements/vanillapay` et le retour `<APP_URL>/paiement/retour`, et faire activer le paiement international et le mobile money. Sans clés, `/paiement` affiche « pas encore activé ».
- **Simulateur local** (`src/app/simulateur-vanillapay/`, `src/lib/simulateur-vanillapay.ts`, jamais en production sauf `VANILLAPAY_SIMULATEUR=1`) : mêmes routes que le prestataire (jeton, ouverture, état), page `/simulateur-vanillapay/payer?id=` avec « Paiement réussi », « Paiement échoué », « montant différent » et une case « sans notification » ; il envoie la notification signée à `notif_url` puis renvoie le payeur à `redirect_url`. En local : `VANILLAPAY_BASE=http://localhost:3000/simulateur-vanillapay` et trois clés quelconques. Les scénarios Playwright (`tests/e2e/paiement.spec.ts`) l’utilisent sur le port 3217.

## Modifier le schéma

1. Éditez `prisma/schema.prisma`.
2. Lancez `npm run db:migrate` et donnez un nom à la migration.
3. Le client est régénéré automatiquement ; sinon `npm run db:generate`.

## Bibliothèque de ressources

Documents, vidéos et pages composées, rangés en dossiers et lus dans un lecteur protégé. **Accès ouvert à tous, sans authentification** : aucune connexion, pas de ressource payante ni de dossier restreint. La progression « Terminer » est propre à chaque navigateur grâce à un identifiant anonyme (cookie `cc_lecteur`), sans compte.

- **Données** (Prisma, migrations `bibliotheque` puis `acces_ouvert`) : `Dossier` (nom, couverture, auteur, parent, 5 niveaux au maximum), `Ressource` (titre, catégorie Guide/Modèle/Formation/Rapport, format PDF/DOCX/Vidéo/Photo/Page, taille affichée, pages, couverture, description de 600 caractères, contenu JSON des pages, ordre manuel), `LectureRessource` (étape terminée par lecteur) et `Journal` (actions de l’équipe).
- **Fichiers** : stockés hors de `public/`, dans `stockage/` (ignoré par Git, modifiable avec `STOCKAGE_DIR`). Le fichier d’origine n’est jamais servi au navigateur.
- **Envoi** (`src/lib/ressources/traitement.ts`) : format détecté par la signature du fichier (`%PDF-`, archive zip nommée .docx, `ftyp` pour le MP4, JPEG, PNG, WebP), 490 Mo maximum, lecture en flux. Un PDF est converti en une image PNG par page à 110 dpi : avec `pdftoppm` s’il est installé (`PDFTOPPM_PATH`), sinon avec pdf.js (`scripts/pdf-en-pages.mjs`, `pdfjs-dist` et `@napi-rs/canvas`). Un DOCX passe d’abord par LibreOffice sans interface (`SOFFICE_PATH`) : **LibreOffice n’est pas installé sur la machine de développement**, un DOCX y est donc refusé avec « n’a pas pu être converti, enregistrez-le en PDF ». Une photo devient une page PNG, une vidéo MP4 est gardée telle quelle. La couverture est la page 1 ou la première photo d’une page (JPEG qualité 78), ou une couverture personnalisée. En cas d’échec, tout ce qui a été écrit est effacé.
- **Lecture protégée** : pages servies une à une par `/api/ressources/[id]/pages/[n]` (deux premières tout de suite, les suivantes à la demande, numéro « n / N »), vidéo par `/api/ressources/[id]/video` avec les requêtes Range (réponse 206), fichiers des blocs par `/api/ressources/[id]/blocs/[fichier]`. En-têtes `Cache-Control: private, no-store, max-age=0`, `Content-Disposition: inline`, `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin`, `X-Robots-Tag: noindex, nofollow`. Le lecteur bloque menu contextuel, glisser, copier et Ctrl/Cmd + S, P, C, A, et floute le contenu quand la fenêtre perd le focus, quand l’onglet est masqué et après Impr. écran. Ces protections dissuadent, ce ne sont pas des DRM.
- **Parcours** : un dossier ouvert affiche sa couverture, le nombre de ressources et de vidéos, la progression « X étapes terminées sur N », la carte Auteur, les sous-dossiers en sections et les ressources numérotées. La page de lecture propose « Terminer », les étapes précédente et suivante et la colonne des étapes (terminée, en cours).
- **Format Page** (`src/lib/ressources/blocs.ts`, éditeur dans `src/components/bibliotheque/editeur/`) : blocs Titre (niveau 2 ou 3, alignement, couleur), Texte riche (paragraphes, listes, gras, italique, barré, lien, couleur, taille, alignement, stocké en JSON et non en HTML), Photo avec légende (convertie en WebP qualité 82) et Vidéo (MP4 envoyé ou lien YouTube en mode youtube-nocookie, Vimeo, Google Drive). À l’enregistrement, les fichiers de blocs inutilisés sont effacés.
- **Outils de l’équipe** (`/admin/ressources`, sans authentification comme le reste du back-office) : ajout par fichier avec barre de progression ou page composée, modification, remplacement du fichier, couverture personnalisée ou automatique, suppression ; dossiers avec couverture, auteur et emplacement (refus de ranger un dossier dans sa descendance ou au-delà de 5 niveaux), suppression qui remonte sous-dossiers et ressources d’un niveau ; ordre manuel par glisser-déposer (flèches sur téléphone), sélection multiple, couper, copier (fichiers dupliqués) et coller entre dossiers ; signal « Fichier manquant ».
- **Démonstration** : `npm run db:seed` crée quatre dossiers (dont un parcours « Agenda MECC Digital » avec auteur et sous-dossier) et des PDF, photos et pages composées convertis réellement.
- **Tests** : `npm test` vérifie la détection des formats, la conversion d’un PDF de 20 pages en 20 images, l’arborescence des dossiers (boucles, 5 niveaux) et le nettoyage des blocs et des liens vidéo.

## Déploiement (Docker)

Le `Dockerfile` reprend celui que génère TwinsDeploi (Node 22 Alpine, `npm ci`, `npm run build`, `npm prune --omit=dev`), avec un démarrage par `scripts/demarrer.sh` : lancé en root, il donne le dossier `STOCKAGE_DIR` à l’utilisateur `node`, applique les migrations, puis démarre l’application sous cet utilisateur. Sans cela, le volume persistant monté sur `/data` appartient à root et tout envoi de photo, vidéo ou ressource échoue avec `EACCES`.

- **Variables** : `DATABASE_URL`, `STOCKAGE_DIR=/data` (avec un volume monté sur `/data`).
- **Migrations** : `scripts/demarrer.sh` lance `prisma migrate deploy` avant l'application ; sans migration en attente, la commande ne fait rien. Si elle échoue, le conteneur ne démarre pas : la cause est dans les logs du déploiement.
- **Vérification** : au démarrage, les logs affichent `Stockage prêt : /data`.

## Liaison avec Facebook et Instagram

Quand un participant colle le lien de sa publication (défis 1 et 3), l'application :

1. **Analyse le lien** (`src/lib/social/links.ts`) : accepte les liens de publication, photo, vidéo, reel, partage et `fb.watch` de Facebook, ainsi que `/p/`, `/reel/` et `/tv/` d'Instagram. Les profils, les pages et les autres sites sont refusés avec un message clair. Le lien est normalisé (suivi publicitaire retiré) avant d'être enregistré.
2. **Affiche un aperçu** de la vraie publication (`src/components/social/PostEmbed.tsx`) grâce aux extraits intégrables officiels de Facebook et d'Instagram. Aucune clé n'est nécessaire, mais la publication doit être publique. L'aperçu se retrouve ensuite dans le résumé de la participation.
3. **Vérifie la publication côté serveur** (`GET /api/publications/check?url=…`, `src/lib/social/meta.ts`) avec l'API oEmbed de Meta, uniquement si `META_APP_ID` et `META_APP_SECRET` sont renseignés dans `.env`. Une publication privée ou supprimée est alors refusée avant l'envoi. Sans ces clés, la route répond `verification: "disabled"` et la participation est acceptée sur la forme.

### Réactions réelles (défi 3 000 000 Ar)

Facebook refuse de lire ses propres adresses avec la clé d’application (« Facebook URLs cannot be crawled »). Le vrai nombre de réactions passe donc par **Facebook Login** : le participant connecte le compte qui a publié (`GET /api/facebook/login` → dialogue OAuth → `/api/facebook/callback`, jeton longue durée dans un cookie `httpOnly` de 60 jours, `/api/facebook/status` et `/api/facebook/logout`). La route `GET /api/publications/reactions?url=…` (`src/lib/social/facebook.ts`) lit alors `reactions.summary(total_count)`, les commentaires et les partages sur la publication : par son `fbid` pour une photo, sinon en la retrouvant dans `/me/posts` par son identifiant. Sur la page du défi, « Ma publication » affiche la valeur réelle avec l’heure du relevé et un bouton « Actualiser » ; le compteur simulé a été retiré pour cette ligne.

Limites de Meta : une publication dans un **groupe** n’est pas lisible (message explicite, publier sur son profil en Public) ; Instagram personnel non plus. Permissions demandées : `public_profile`, `user_posts`, `user_photos` (modifiables par `META_SCOPES`). Les clés `META_BUSINESS_APP_ID` / `META_BUSINESS_APP_SECRET`, si renseignées, priment sur `META_APP_ID` / `META_APP_SECRET`. Attention : une app Meta de type **Business** n’a pas accès à `user_posts` (erreur « Invalid Scopes » à la connexion) ; il faut une app de type **Consommateur** pour lire les publications d’un profil personnel. En mode développement de l’app Meta, elles fonctionnent pour les administrateurs et testeurs de l’app ; pour tous les participants, elles doivent passer l’App Review de Meta. Côté app Meta : ajouter le produit Facebook Login et déclarer l’URI de redirection (`http://localhost:3000/api/facebook/callback` en local, l’URL publique en production, ou `META_REDIRECT_URI`).

Variables d'environnement (jamais dans Git) : `META_APP_ID`, `META_APP_SECRET`, `META_GRAPH_VERSION` (défaut `v23.0`). Modèle dans `.env.example`.
